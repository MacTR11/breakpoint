# Breakpoint

A Python practice and competition platform for A Level Computer Science (see README.md), run by one teacher for their own students. The focus is programming: writing code, fixing broken code and reading code. Theory content was deliberately removed.

- `npm run dev` / `npm run build` / `npm run lint` / `npm run verify` (proves every coding challenge in `content/problems` against the judge, and that its points follow `src/lib/points.ts`) / `npm run check` (the rules worked out on demand: homework states, paste flags, points, special days) / `python3 scripts/check-puzzles.py` (recomputes puzzle answers) / `npm run e2e` (Playwright, in `e2e/`: starts its own site on port 3100 with its own `prisma/e2e.db`, rebuilt each run; `e2e/prepare.ts` refuses any other database. Set `PLAYWRIGHT_CHROMIUM` to use a Chromium already installed).
- After changing `prisma/schema.prisma`: `npx prisma db push`, then restart the dev server (it caches the Prisma client). After changing `content/`: `npm run verify && npm run db:seed`.
- If new Tailwind classes do not show up in the running dev server, restart it: its stylesheet scan can go stale.
- Marking logic lives in `public/judge/harness.mjs` and is shared by the browser worker ("Run") and the server judge ("Submit"); change it in one place and re-run `npx tsx scripts/judge-smoke.ts`.
- The debugger and console (`public/judge/tracer.mjs`, in the same browser worker as "Run") only run the student's own code with calls they type or the visible examples. They mark nothing and must never be handed hidden tests.
- Expected answers, hidden tests and hints not yet paid for must never reach the browser.
- The command palette's list (`/api/palette`) holds only titles the user could already open: for a student, Practice and competitions running now (never a pending competition's challenges). Students are not told that a homework challenge is held for a competition, for the same reason. `submitCode` strips hidden results; `judge()` sends inputs only; the problem page sends only unlocked hints. A locked puzzle's answer is revealed only when no live competition uses it.
- Accounts: there is no sign-up and no Google sign-in. The one teacher signs in with `TEACHER_USERNAME` / `TEACHER_PASSWORD` from `.env` (never stored in the database). Students are created by the teacher, singly or by CSV (`src/app/(app)/teacher/students/actions.ts`, `src/lib/accounts.ts`). Passwords are scrypt hashes (`src/lib/passwords.ts`) and are only readable at the moment they are set, which is when the sign-in sheet is shown. Changing a password raises `sessionEpoch`, which signs old sessions out; wrong attempts are throttled per username (`src/lib/throttle.ts`).
- Never log, return or store a readable password anywhere except the one-off sign-in sheet, and never weaken the throttle or the hash to make testing easier.
- Every server action and route handler checks the user itself (`getCurrentUser`, or `assertTeacher` from `src/lib/session.ts`); layouts alone are not a security boundary. A `"use server"` file may export only async functions (and types).
- `useActionState` forms get their fields back from the action on failure (`FormState.values`), because React resets a form when its action finishes.
- Scores are solves minus `Submission.penalty`; any new total must subtract penalties (`pointsOf`, `leaderboard`, `studentSummaries`, `classStandings`, `topicGrid`). Points follow `src/lib/points.ts` (write 10/25/50, fix 10/20/40, put in order 5/10/20, trace table 10/15/25, puzzle 5/10/20; First steps 5; exam questions 5 a mark, from the `**[N marks]**` line), and challenge files must carry matching `points`. Hint tokens are derived, not stored: see `hintWallet` in `src/lib/hints.ts`.
- Solving goes through `recordSolve` in `src/lib/solve.ts`, which also handles the hint token, the daily bonus and new awards. Awards, streaks and the daily pick are derived on demand; only `DailyBonus` rows are stored. Days are UK calendar days (`londonDay`).
- Classes are compared on average points per student, counting students who have not started (`classStandings` in `src/lib/classes.ts`). Each class's colour comes from its place in name order (`allClasses`, `classColor`).
- Paste tracking: the editor counts typed and pasted characters and time in view (`src/lib/typing-counts.ts`, judged on CodeMirror's transactions, so drops and big keyboard insertions count) and sends them with each submission, where `cleanTelemetry` checks them. `pasteFlag` / `mightBeFlagged` in `src/lib/integrity.ts` are the one rule for a flag, and `flagsByChallenge` counts it once per student per challenge (the counts build up over a draft). Record or block is the `pasteMode` `Setting` row. Flags are for the teacher only: never show them to students or put them on reports, and call them a reason for a conversation, not proof.
- Homework, mock-paper marks and the bell's notifications are derived on demand like awards (`src/lib/homework.ts`, `mock.ts`, `notifications.ts`); only `Homework` and `MockPaper` rows are stored. Homework may only use challenges in Practice. A homework challenge students cannot open counts only once solved, and after the due date it is judged by whether it could be opened at the due date (`ContestProblem.createdAt`), so past results never change. The bell counts notices by key against the keys the browser has seen, never by comparing clocks. While a mock paper runs, its questions show no hints, mark scheme, model answer or earlier code, and `unlockHint` refuses.
- Easter eggs (`src/components/easter-eggs.tsx`, `src/lib/eggs.ts`, `special-days.ts`, the secret awards) never change a score, must respect `prefers-reduced-motion`, and are listed in the README.
- A contest with null dates is an unscheduled pack: use `isLive` / `isPending` from `src/lib/problems.ts` rather than comparing dates directly.
- A challenge is `kind` CODE or PUZZLE; a CODE challenge has `style` WRITE, FIX (the starter code is deliberately broken) or ORDER (the starter is the shuffled lines, marked by running the arranged code). A PUZZLE with `style` TRACE is a trace table (`options` is a `TraceSpec`, `answer` the full table; `submitTrace` returns only which boxes are wrong). ORDER and TRACE are edited as files only. Every challenge needs a `track` and at least one hint.
- Live lessons (`src/lib/live.ts`): one `LiveLesson` at a time, ending itself after two hours; students' browsers poll `/api/live`. The weekly class race (`src/lib/race.ts`) runs Monday to Monday, UK time.
- Every challenge must be original. Do not copy Bebras, LeetCode or exam-board questions: the "exam" topic is written in the style of the H446 papers (a scenario, parts, marks, a mark scheme) but none of it is taken from them.
- A CODE challenge may have an `--- explanation` section, which is its mark scheme. It and the model answer are shown only once the student has solved the challenge, and never while a live competition is using it (teachers always see them).
- Design follows DESIGN.md ("Playground": grey page, solid rounded cards, rounded display type, each topic a solid block of its own colour, light and dark), which the owner chose from mock-ups after rejecting several other looks, including glass. Read it before any UI work, and show options before restyling. Colours come from the CSS variables so both themes work; statuses are plain words; no glass, blur, gradients, shadows or glows.
